## Interpretation and evidence boundaries

- Rows describe grants declared in code, not a live effective-access audit. An omitted grant is not an explicit deny. Inherited roles, manual assignments, tenant settings, Azure DevOps permissions and actual group membership can add access outside this matrix.
- `current` means the identity executing layer 0 (`data.azurerm_client_config.current`). Build logs name Lab Admin, but the Terraform expression does not hard-code that human account.
- Scope abbreviations: foundation RG = foundation resource group; network RG = network resource group; app RG = application resource group; app-vault RG = dedicated application Key Vault resource group. Each belongs to the stated environment unless explicitly shared.
- Azure management-plane roles do not automatically grant Entra directory permissions or Key Vault data-plane access. Resource management can nevertheless enable indirect access (for example, changing application code running with an identity). Network reachability, policies, immutability and management locks further constrain authorized operations.
- “Cannot” below means not granted by the reviewed assignments, unless explicitly described as a configured restriction. It is not a guarantee against privilege escalation by a broader inherited identity.

## PIM and Conditional Access

- All three admin-prod eligible roles require activation with justification and MFA, maximum two hours. Eligible assignments have no required expiration. No approval requirement is declared in activation_rules.
- Two tenant Conditional Access policies target admin-prod for all applications/client app types: one matches Dev/Test NAT addresses, one matches deviceCodeFlow. Both use `enabledForReportingButNotEnforced` and a block grant control. They evaluate/report a would-be block; they DO NOT block sign-in while report-only.
- The layer 0 executing identity is explicitly excluded (reported Lab Admin). These policies do not target the pipeline managed identities or all production app users.
- admin-prod has permanent Reader and Virtual Machine User Login in addition to eligible roles. “No permanent rights” is inaccurate.

## Important boundaries and unresolved access facts

- No layer 0 infrastructure pipeline identity is declared; layer 0 bootstrap/identity/role changes remain administrator work in this code.
- No Terraform Azure role gives a pipeline Microsoft Graph directory access. Dev layer 2 uses the supplied app_client_id variable. Test and Prod layer 2 still declare data.azuread_application.app lookups; that configuration needs directory lookup access or the same refactor, so “no Graph lookup in all environments” is not yet supported.
- Foundation vaults (certificate and admin) keep public network access enabled with network ACLs/policy exemptions; only application vaults disable public access. Role authorization and network reachability are separate.
- App-user groups grant sign-in, not management. /health is anonymously accessible to network-authorized clients by design; group restriction applies to protected app routes.
- No explicit Key Vault secrets write role is declared for infra/destroy identities. Creating a vault is management-plane work; seeding or deleting secrets is a separate data-plane permission.
- Production delete locks block applicable delete operations until removed; Terraform prevent_destroy is a Terraform lifecycle guard, not an Azure RBAC deny.
- Test and Prod infra-l1/infra-l2 lack the additional cross-layer rights listed for Dev at this snapshot; successful local administrator applies do not prove pipeline readiness.
- Azure DevOps approval checks, pool/service-connection permissions, repository rights and human group memberships are configured outside these Terraform resources. Build records report production approval, but this matrix cannot prove live authorization.
