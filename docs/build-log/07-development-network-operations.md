**Status:** Completed. Development layer 1 (network and operations) is built, verified from inside the network, and matches the configuration (`terraform plan` reports no changes).

**Execution:** Peter edited the configuration and ran all commands, guided by Claude. Layer 1 was built locally from `infra/environments/development/layer-1-network-operations/` with the Lab Admin account, using the temporary state role from `temporary.tf` in layer 0 (option B). The `dev-infra-l1` pipeline takes over this layer later; `temporary.tf` is removed at that point.

## Configuration approach

- Layer 1 reads layer 0 resources through data sources by their fixed names (no `terraform_remote_state`).
- The state is stored in the `tfstate-layer1` container of the development state storage account.
- Real values (subscription, Azure DevOps organization, service principal identifiers) are kept in the ignored `development.tfvars`. `development.example.tfvars` shows placeholders.

## Network security

One network security group per subnet (`nsg-sits-dev-<subnet>-swc`) and five application security groups: `ops-vm`, `pe-webapp`, `pe-kv-app`, `pe-kv-cert`, `pe-kv-admin`. Every group ends with an explicit `deny-all-inbound` rule (priority 4000) before the Azure default `AllowVnetInBound`.

| Subnet | Allowed inbound |
| --- | --- |
| `snet-ops` | RDP 3389 from Bastion Developer (168.63.129.16) to `ops-vm`. Outbound from `ops-vm` to `AzureResourceManager` is denied. |
| `snet-agw` | HTTPS 443 from `ops-vm`; `GatewayManager` 65200-65535; `AzureLoadBalancer` |
| `snet-pe` | Web app endpoint from `snet-agw` and `snet-agents-app`; application vault from `snet-app` and `snet-agents-infra`; certificate vault from `snet-agw` and `snet-agents-infra`; admin vault from `snet-agents-infra` (all on 443) |
| `snet-agents-infra`, `snet-agents-app`, `snet-app` | None |

## Flow logs

| Resource | Layer | Configuration |
| --- | --- | --- |
| Storage account `stsitsflowdevswc` | 0 | Permanent, so records survive a layer 1 destroy. TLS 1.2, HTTPS only, no public blob access. |
| Flow log `fl-sits-dev-vnet-swc` | 1 | Virtual network flow log (version 2) under the Azure-managed `NetworkWatcher_swedencentral`, 30-day retention, Traffic Analytics every 10 minutes to the development Log Analytics workspace |

Deviation: shared key access is enabled on the flow log storage account. Network Watcher can write with a user-assigned managed identity, but `azurerm_network_watcher_flow_log` in AzureRM 5.7 cannot configure one. The account stores network logs only. Retention is set on the flow log, because the flow log manages the lifecycle rule of its storage account.

## Issues and fixes

- The Application Gateway subnet delegation showed drift, because Azure stores `subnets/join/action`. The code was aligned with Azure.
- The Ops VM failed with `OperationNotAllowed`: the subscription has zero quota for the DSv5 family in Sweden Central. `Standard_D2s_v4` is not offered to the subscription in this region. `az vm list-skus --all` showed `Standard_D2s_v6` without restriction and the Dsv6 family has quota, so the VM uses `Standard_D2s_v6` with the NVMe disk controller.
- Managed DevOps Pools have their own quota (queried through the `Microsoft.DevOpsInfrastructure` usages API, version `2024-04-04-preview`). The DADSv5 family has 5 vCPUs, so both pools use `Standard_D2ads_v5`.
- After the pools were created, Azure stored the image as `ubuntu-24.04` with two aliases. The code was aligned with Azure to remove the drift.
- A command pasted twice into PowerShell caused a parser error and changed nothing; it was run again once.

## Decisions

- Option B: layer 1 was built locally with a temporary state role before the pipeline takes over.
- The Ops VM is an observation point inside the network, not an administration workstation: it cannot reach Azure Resource Manager.
- Flow log storage lives in layer 0 (option A), with 30-day retention to match the Log Analytics workspace.
- The network roles for Managed DevOps Pools are granted in layer 0 on the network resource group.
